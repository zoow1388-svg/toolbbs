# 恢复规则

恢复工作流时先读取 Codex 任务实际状态、目标项目 Git 状态和状态文件，不得直接沿用中断前结论。

1. 核对项目绝对路径和任务 ID。
2. 核对 Git 基线、分支和未提交修改。
3. 核对最后派发事件是否已送达以及任务是否已响应。
4. 将版本不一致或时间早于最后派发的结果标记为 `stale`。
5. 对已送达但未记账的事件补充审计记录，不重复派发。
6. 对状态文件已记录但实际未送达的任务，报告不一致并等待决定。
7. 不自动恢复 `failed`、`cancelled`、`blocked` 或 `stale` 任务。
8. 运行管理器的 `audit`；事件序号断裂、状态序号不一致或存在 `.tmp.`/`.bak.` 残留时停止自动恢复。
9. 旧版状态缺少 v0.2 字段时，由状态模块在下一次合法写操作中补充默认值，不手工覆盖原文件。
10. v0.3 恢复先运行 `reconcile`：准备未发送则发送现有信封，已发送则等待确认，已确认则等待结果，已收结果则验证；`manual_review` 必须停止。
11. 使用保存的 `read_cursor` 继续读取，禁止从头重复处理旧消息；不得为同一任务重新生成派发编号。
12. 恢复前校验发送回执和最近任务观察的 SHA-256；文件缺失或哈希变化时进入人工检查。
13. 宿主未返回消息 ID 时，以原始发送回执、任务身份、派发编号和游标联合证明投递，不得补造消息 ID。
14. v0.5 恢复先导入最新等待快照；revision 必须严格递增，同一 revision 不得重复记账。
15. 等待快照出现完整 turn ID 和 item ID 后，`reconcile` 返回 `fetch_full_result`。必须通过 `read_thread` 和精确 ID 提取完整结果，不能使用可能被截断的等待预览。
16. 恢复前同时校验等待快照、其引用的原始响应和已提取结果的 SHA-256；任一证据被替换即停止。
17. v0.6 不接受调用者自报 `Verified`。结果收到后必须执行 `verify-result` 生成验证回执；恢复时有回执则先审计，无回执则重新执行确定性验证。
18. 完成任务前校验原始结果、规范化结果和验证回执三者哈希及身份一致；验证后任一文件变化都进入人工检查。
19. 从 v0.5 升级时，缺少回执的历史完成任务保留 `completed`，但改标为 `legacy-unverified` 且不得放行新依赖；不要补造历史回执。
20. v0.7 恢复时生成工作流级动作计划，不再手工拼接多个单任务 `reconcile` 结果。执行动作前必须确认计划事件序号和两个状态文件哈希仍然一致。
21. 旧动作计划只可丢弃并重新生成，不得修改其中的游标、身份或操作后继续使用。

清理只限本次流程创建并可确认无用的临时文件；不得删除用途不明文件、用户修改、生产数据或动态入口。
